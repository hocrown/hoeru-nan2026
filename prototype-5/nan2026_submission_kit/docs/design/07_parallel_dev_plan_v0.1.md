# 병렬 개발 운영 계획 v0.1 — 트랙 분해 · 워크트리 전략 · 태스크 정의서

> 2026-08-10 / P1 프로토타입 스펙 v0.1 기준. 도구: Paseo (멀티 에이전트 오케스트레이션) + git worktree.
> 원칙: **병렬화는 P1 통과 이후.** 코어 재미 검증 루프(구현→플레이→조정)는 단일 에이전트 + 밀착 리뷰.

---

## 1. 단계별 운영 게이트

| 단계 | 운영 방식 | 이유 |
|---|---|---|
| **P1 (코어 검증)** | 단일 에이전트 1개 + 사람 밀착 리뷰 | 병목이 에이전트 처리량이 아니라 사람의 플레이 판단. 병렬화 이득 없음 |
| **P2 (공명 검증)** | 단일 에이전트 유지, 병렬 트랙 1개(T1 에셋 파이프라인)만 선행 가동 | T1은 코어 코드와 무충돌 — 조기 착수 가능 |
| **P1·P2 통과 후 (본제작 진입)** | 4트랙 병렬 가동 | 아래 §2 |
- 게이트 판정: P1 KPI(스펙 §7) 충족 시에만 병렬 확대. 미충족 시 병렬화 논의 자체를 보류.

## 2. 트랙 분해 (독립성 기준)

| 트랙 | 내용 | 주요 산출 경로 | 코어 코드 충돌 |
|---|---|---|---|
| **T0. 코어 게임플레이** | 전투·시너지·웨이브·보스 (메인 트랙) | `game/core/`, `game/units/` | — (기준 트랙) |
| **T1. 에셋 파이프라인** | sprite-gen 요청 작성·실행, manifest→Godot SpriteFrames 변환 유틸 | `tools/asset_pipeline/`, `assets/` | 없음 |
| **T2. 데이터 파이프라인** | 밸런싱 xlsx → 게임 데이터(JSON) 익스포터, 스키마 검증 | `tools/data_export/`, `game/data/*.json` | 낮음 (T0는 JSON을 읽기만) |
| **T3. UI/화면** | 메뉴, 인연록, 시너지 카운터 UI, 헌책방 허브 화면 | `game/ui/` | 낮음 (씬 분리) |
| **T4. 텔레메트리** | KPI 로그 수집(CSV), 분석 스크립트, 사망 히트맵 | `tools/telemetry/`, `game/telemetry/` | 낮음 (훅 1파일) |
- 충돌 방지 규칙: 트랙 간 공유 지점은 **인터페이스 파일로 고정** (T2↔T0: JSON 스키마 / T4↔T0: 이벤트 훅 시그니처 / T3↔T0: 시그널 이름). 인터페이스 변경은 T0에서만, 변경 시 전 트랙 공지.

## 3. 워크트리 · 브랜치 전략

```
repo/
├─ main                      # 항상 실행 가능한 상태만 머지
├─ worktrees/
│  ├─ t0-core      (branch: track/core)
│  ├─ t1-assets    (branch: track/assets)
│  ├─ t2-data      (branch: track/data)
│  ├─ t3-ui        (branch: track/ui)
│  └─ t4-telemetry (branch: track/telemetry)
```
- Paseo에서 에이전트 1개 = 워크트리 1개 고정 배치 (같은 폴더 동시 수정 금지 — Paseo 알려진 제약).
- 브랜치 수명: 태스크 단위로 짧게. `track/data` 위에 `task/data-xlsx-exporter` 식 파생 → 완료 즉시 track 브랜치로 머지 → track→main은 §6 리듬으로.
- 머지 기준 (전 트랙 공통 DoD 최소선): ① 빌드/실행 성공 ② 해당 트랙 스모크 테스트 통과 ③ 사람 리뷰 1회. **에이전트끼리 상호 리뷰는 참고용, 최종 승인은 항상 사람.**

## 4. 태스크 정의서

### 4-0. 템플릿
```
[태스크 ID] 트랙-번호 (예: T2-01)
목표: 한 문장
입력: 참조 문서/파일 (경로 명시)
산출물: 파일 경로 + 형식
완료 기준(DoD): 검증 가능한 조건 목록
금지사항: 건드리면 안 되는 영역
배정: 모델/에이전트 (A/B 대상 여부)
```

### 4-1. T1-01 — sprite-gen 파이프라인 구축
- 목표: 적 3종(잡귀·원귀·돌귀)의 스프라이트 아틀라스를 sprite-gen으로 생성하는 파이프라인 완성.
- 입력: P1 스펙 §5(적 스펙), 아트 파이프라인 v0.1 §7(프롬프트 시드 형식), aldegad/sprite-gen SKILL.md.
- 산출물: `tools/asset_pipeline/requests/*.json` (sprite-request 3종), `assets/enemies/*/sprite-sheet-alpha.png` + `manifest.json`.
- DoD: 3종 × 4상태(idle/move/attack/death) 아틀라스 생성 · 크로마키 잔여 픽셀 없음(수동 확인) · manifest frame_layout 유효.
- 금지: `game/` 하위 수정 금지.

### 4-2. T1-02 — manifest → Godot 변환 유틸
- 목표: sprite-gen manifest.json을 Godot SpriteFrames(.tres)로 변환하는 스크립트.
- 입력: T1-01 산출물, Godot 4 SpriteFrames 포맷 문서.
- 산출물: `tools/asset_pipeline/manifest_to_spriteframes.py` + 사용법 README.
- DoD: T1-01의 3종 전부 변환 → Godot에서 재생 확인 스크린샷 · 프레임 순서/타이밍 manifest와 일치.
- 금지: 아틀라스 원본 재가공 금지 (변환만).

### 4-3. T2-01 — 밸런싱 xlsx 익스포터
- 목표: `jangsam_balance_v0.1.xlsx`(경지체계 탭)와 시너지 스펙 수치를 게임이 읽는 JSON으로 내보내는 도구.
- 입력: 밸런싱 xlsx, 시너지 스펙 v0.1, P1 스펙 §3~4.
- 산출물: `tools/data_export/export.py`, `game/data/tiers.json`, `game/data/synergies.json`, `game/data/units.json` + JSON 스키마 파일.
- DoD: 익스포트 후 스키마 검증 통과 · xlsx 수치 변경 → 재익스포트 → 게임 반영의 왕복 1회 시연 · T0와 합의된 스키마 동결.
- 금지: xlsx 내부 수식 수정 금지 (읽기 전용).

### 4-4. T3-01 — 시너지 카운터 UI
- 목표: 화면 좌측 태그 카운터 (2/4 점등 + 단계 상승 플래시·사운드 훅).
- 입력: P1 스펙 §4, T2 synergies.json 스키마.
- 산출물: `game/ui/synergy_panel.tscn/.gd`.
- DoD: T0의 태그 변경 시그널 구독만으로 동작 (T0 코드 수정 0줄) · 단계 상승 연출 재생 확인.
- 금지: `game/core/` 수정 금지 — 필요한 시그널이 없으면 T0에 요청서 발행.

### 4-5. T4-01 — KPI 로거
- 목표: P1 스펙 §7의 로그(사망 시각/원인, 승급 선택, 태그 도달, 저스트 판정)를 CSV로 덤프.
- 입력: P1 스펙 §7, T0 이벤트 훅 시그니처.
- 산출물: `game/telemetry/logger.gd`, `tools/telemetry/analyze.py` (사망 시각 히스토그램 1종 포함).
- DoD: 1회 플레이 → CSV 생성 → analyze.py가 그래프 산출 · 프레임 드랍 유발 없음(로그는 버퍼링 후 종료 시 기록).
- 금지: 게임 로직 분기에 로거 코드 삽입 금지 (이벤트 구독만).

## 5. 모델 A/B 프로토콜 (Claude Fable 5 vs GPT-5.6 Sol)

- 방식: **동일 태스크 정의서를 두 모델에 각각 배정** (Paseo에서 워크트리 2개로 격리). 1차 대상: T1-02와 T2-01 (완료 기준이 기계적으로 검증 가능해 비교가 공정).
- 측정 항목: ① DoD 도달 여부/재시도 횟수 ② 사람 개입 횟수(막혀서 지시가 필요했던 지점) ③ 소요 시간 ④ 비용 ⑤ 산출 코드의 수정 용이성 (1주 후 소규모 변경 요청을 던져 재평가).
- 판정: 트랙별로 승자 배정 — "전 트랙 단일 모델"을 강제하지 않음. 벤치마크 문서가 아니라 **우리 코드베이스의 실측**으로 결정.
- 재평가 주기: 메이저 모델 업데이트 시 1회 (상시 A/B는 낭비).

## 6. 통합 리듬 & 운영 규칙

- **일일**: 각 트랙 → track 브랜치 머지 (DoD 충족분만). Paseo 모바일로 진행 확인은 자유, **승인 행위는 데스크톱에서** (실수 방지).
- **주 2회**: track → main 통합 + 전 트랙 스모크 테스트 + 통합 빌드 1회 플레이.
- **인터페이스 변경**: T0 단독 권한. 변경 시 해당 스키마/시그니처 파일 diff를 전 트랙 태스크 정의서에 반영 후 재개.
- **에이전트 폭주 방지**: 태스크 정의서 밖의 "개선"은 금지 조항으로 명시 (스코프 크리프의 주범). 제안은 코드가 아니라 노트로.
